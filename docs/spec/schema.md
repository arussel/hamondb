# Schema

Rules governing the shape of a table: how primary keys, regular columns,
computed columns, and indexes are declared and what constraints the
`#[derive(Table)]` macro enforces. Also covers slots and resources, which
share the `Table` machinery.

### HMN-SCHEMA-001 — One primary key per table
A struct passed to `#[derive(Table)]` must have exactly one field annotated
`#[primary_key]`. Absence yields a compile-time error `No primary key found`.

### HMN-SCHEMA-002 — Primary key type
`T::PrimaryKey` is set to the type of the `#[primary_key]` field. It must
satisfy `Eq + Hash + Clone + Send + Sync + 'static`. These bounds are
enforced at the `Table` impl site, not inside the macro.

### HMN-SCHEMA-003 — Composite primary keys are not supported by the derive macro
The macro accepts at most one `#[primary_key]` attribute. For a composite
key, implement `Table` manually and use the tuple `IntoPrimaryKey`
implementations in `table.rs` (e.g. `(Column<T, A>, Column<T, B>)`).

### HMN-SCHEMA-004 — Column handle per non-skipped field
For every non-`#[skip]` field `name: FieldType`, the derive macro generates
`pub const <SHOUTY_SNAKE_CASE_NAME>: Column<Self, FieldType>`. The `id` on
the generated handle equals the field's index in declaration order.

### HMN-SCHEMA-005 — Column `id` stability
A column's `id` is its declaration-order index among all fields (including
`#[skip]` ones). Reordering or inserting fields changes other columns' ids.
Call sites that persist column ids externally are therefore brittle.

> Is this intended as part of the public contract, or an implementation
> detail that could switch to a different id scheme (e.g. stable hash of
> field name)? Code: `hamondb-macro/src/table.rs:97-98`.

### HMN-SCHEMA-006 — `#[skip]` excludes a field from the column registry
A field marked `#[skip]` is stored on the struct and clonable, but no column
handle is generated and the field is not registered in the table's
`regular_columns`. Such a field cannot be read via `row.get(…)` or named in
a computed-column dependency.

### HMN-SCHEMA-007 — `#[skip]` is mutually exclusive with other field attributes
Combining `#[skip]` with any of `#[primary_key]`, `#[index]`, or `#[computed]`
is a compile-time error.

### HMN-SCHEMA-008 — `#[index]` generates a secondary index handle
`#[index]` on field `foo: V` generates
`pub const FOO_IDX: Index<Self, V>`. `#[index(NAME)]` overrides the handle
name. The derive assigns each index a dense numeric id in declaration order,
starting at 0.

### HMN-SCHEMA-009 — Index value type is the field type
The value type of an index generated by `#[index]` is the exact field type.
`lookup_index` must be called with a value of that exact type (passing e.g.
`&i32` for a `u32`-typed index is a compile error).

### HMN-SCHEMA-010 — `#[computed]` requires a same-named method
A field `foo: V` marked `#[computed]` requires a method
`fn foo(row: &Row<Self>, ctx: &Ctx) -> V` on the owning impl. The macro
references it by path; a missing method is a compile error at the
referencing site.

### HMN-SCHEMA-011 — Computed column initial value is overwritten
The value supplied at `insert`-time for a `#[computed]` field is discarded.
The computed function is evaluated during insert and its return value is
what is stored.

### HMN-SCHEMA-012 — Computed-column dependencies on other computed columns must be declared
A `#[computed]` field that reads another `#[computed]` field must list the
latter in `#[computed(DEP1, DEP2, …)]`. A read through `row.get(Self::DEP)`
of an undeclared computed column panics the compute function at runtime.

### HMN-SCHEMA-013 — Cycle rejection at build time
If `#[computed(…)]` declarations form a cycle, `HamonBuilder::build()`
panics with `computed column cycle detected`.

### HMN-SCHEMA-014 — Slot declarations
`slot!(vis NAME: Type)` generates a zero-sized marker type and a
`pub const NAME: Slot<Marker, Type>` whose name string is
`concat!(module_path!(), "::", "NAME")`. Slots satisfy
`Type: Clone + PartialEq + Send + Sync + 'static`.

### HMN-SCHEMA-015 — Resource declarations
`resource!(vis NAME: Type)` generates a zero-sized marker and a
`pub const NAME: Resource<Marker, Type>`. Resources satisfy
`Type: Send + Sync + 'static`.

### HMN-SCHEMA-016 — Builder registration is single-use
`register_slot` panics with `slot already exists` when the same slot type
is registered twice. `register_resource` panics with `resource already
exists` likewise. `register_feeder` panics on duplicate name.

### HMN-SCHEMA-017 — Listener registration requires a prior table registration
`register_listener::<T>` panics with `table not registered` if the table
`T` has not been registered via `register_table` or `register` before the
listener call.

### HMN-SCHEMA-018 — Slot is modeled as a one-row table
A slot's state is stored as a `SlotRow<M, V>` with primary key `()`. All
read / write operations on slots go through the same code paths as regular
table operations.
